# Agent Note: Multi-provider pack and whole-session engines

Status: implemented

English | [中文](2026-08-14-multi-provider-pack-and-engines.zh.md)

## Problem

Deployments asked for third-party model providers and external coding agents, each with its own credential story. The generic pi-ai adapter (`dsh-llm-pi-ai`) already ships catalogs for Gemini (`google`), MiniMax (`minimax`), and Kimi (`kimi-coding`) but mounts dormant in `dsh-base` — activating them is a settings-document exercise, not a shippable layer. The Claude Code (official Agent SDK) and Codex (official `codex app-server`) delegation backends exist as packages but appear in no shipped composition, and nothing documents or runs a whole session on either engine. The question was whether third-party support needs new adapters, a loop replacement, or a composition-only answer.

## Decision

**A pack bundle, not new adapters.** `@deepseek-ai/dsh-multi-provider` (`packages/bundle/multi-provider`) is an optional profile layer over `dsh-base`. Its patch activates four pi-ai routes with curated model catalogs and credential references (`GOOGLE_API_KEY`, `MINIMAX_API_KEY`, `KIMI_CODING_API_KEY`, `ANTHROPIC_API_KEY` — the last is the key-based Claude API), and inserts the `subagent-codex` / `subagent-claude-code` rows plus their model-facing tool rows (`subagent_codex`, `subagent_claude_code`) with `disabled: true` — the shipped-profile posture: providers load on the host, no child process starts until a tool call, and no composed agent grows the delegation tools by default. The runnable reference is `examples/multi-provider`, whose `llm-pi-ai` providers dict mirrors the pack patch; `examples/multi-provider/tests/providers.spec.ts` enforces the match mechanically. The demo bin (`packages/examples/multi-provider-demo`) lists providers keyless, runs one task per key-based provider, and routes `run --provider claude-code|codex` to the delegation backends (native OAuth, no key); a failed key-based turn reports the durable `turn/end` error (e.g. `MISSING_CREDENTIAL` naming the key) instead of a generic empty reply. The keyed suites exercise a live turn per key-based provider and a live delegation per backend under native OAuth, including through the demo bin's engine route.

**Engines as selectable LLM providers via the adapter seam, not a loop change.** `@deepseek-ai/dsh-llm-engine` subclasses `LlmAdapter` and registers `claude-code` and `codex` as provider routes on `ctx.llm` (model id `native`), backed by the same `ctx.subagents` backends: a session whose model selection names one of these routes runs every turn through the local CLI with its OAuth state — the web Models picker lists them like any provider. Each `stream()` sends the latest DIRECT user prompt (synthetic context injections are excluded by source kind), forwards the engine's live text deltas as `text-delta` chunks, closes with the assembled answer and a terminal finish, pins a zero-retry policy (a retry would execute the CLI twice), and refuses empty prompts and auxiliary purposes (compaction, session titles) with error finishes. The engines stay text-only from the harness's perspective: they execute their own tools inside their own process.

**Real model and effort selection, not a fake `native` model.** Each engine route advertises its actual model catalog (`claude-code`: the Claude Opus/Sonnet/Haiku family with capacities; `codex`: the installed app-server's GPT-5.3 Codex models), plus a `native` choice meaning "the CLI's own default — no override sent". Selecting a catalog model reaches the engine (SDK `model`, app-server `turn/start model`), verified live. Every catalog model advertises selectable reasoning efforts (`off`/`low`/`medium`/`high`, plus `xhigh`/`max` for Claude) mapped to the engines' native vocabularies (SDK `effort`/`thinking`, app-server `effort`); the harness materializes the adapter's `high` default when the caller omits one, and the subagent seam carries the selection through the new `reasoningEffort` request field behind the `reasoningEffort` capability.

**Long-lived engine sessions, not fresh-per-turn.** The engines natively support long-lived conversations and streaming — Claude Agent SDK `persistSession`/`resume` and `stream_event` text deltas, Codex `thread/start`/`thread/resume` with `item/agentMessage/delta` notifications (verified against the installed SDK types and the generated 0.147.0 app-server schema). The subagent seam grew optional `continuation` capability + `continueFrom`/`continuationId` request/result fields and a live `updates` channel on `SubagentRun`; both engine backends implement them behind a `continuation: true` config (native-stateful by choice — the one-shot default still touches no native state). The adapter keys engine sessions by the loop-stamped `GenerateOptions.sessionId` and resumes on later turns; the memory e2e proves the engine answers turn 2 from its RESUMED conversation.

**Whole-session engines as an experimental runner, not a loop change.** `examples/engine-session` composes NO harness agent loop: `packages/examples/engine-session-demo` creates a harness session, appends `turn/start` and `user/message`, delegates the whole task through the existing `claude-code` or `codex` subagent provider (native claude.ai / ChatGPT OAuth, no key), appends the engine's final answer as `assistant/message` and the outcome as `turn/end` (surface-eligible appends carry `surfaceOp: 'append'`), flushes the session to JSONL persistence, and prints the answer. The harness owns the durable transcript; the engine owns its loop, tools, and permissions inside the run. Both engines are verified live through the real composition, and the e2e asserts the persisted transcript, not the engine's self-report.

## Alternatives considered

**Dedicated adapter plugins per provider (Gemini/MiniMax/Kimi).** Rejected: pi-ai owns the maintained endpoint/protocol/catalog surface (`google-generative-ai`, `anthropic-messages`, `openai-completions`), and hand-rolled adapters would duplicate owned code and tests against the dependency policy. Config-only activation keeps the pack a patch list.

**The engines as `LlmAdapter` routes (main-loop providers).** Rejected: the Agent SDK and app-server are full agents that execute their own tool loops; a harness `llm/stream` consumer cannot translate their per-turn behavior into `StreamChunk`s without bypassing the harness's tool execution, sandbox, and session-log invariants. The delegation seam (`ctx.subagents`) is the honest integration point, and the engine-session runner is the whole-session shape built on it.

**Reusing the multi-provider leaf for engine sessions.** Rejected for composition clarity: the engine leaf mounts only subprocess, subagent, the two backends, the session store, and persistence — no agent spine, no adapters — so "no harness loop" is structurally true, not incidental.

## Consequences

Key-based third-party providers ship as configuration on the maintained adapter (now including the key-based Claude API route); the pack keeps the leaf and bundle patch in sync by test. The one shared "final answer" aggregations were extracted while wiring the engines into the demo bin: `textOfBlocks(content)` (`dsh-llm`) joins text blocks, and `lastAssistantText(events, fromSeq)` (`dsh-session`) is the single definition of a session's final answer, used by the headless runner and every demo driver. The engine adapter makes local OAuth CLIs first-class providers in any profile that composes it (the web app included): selecting Claude Code or Codex routes the session's turns through the local CLI, with the trade-offs that engine turns carry no cross-turn memory, no tool calls surface in the session log, runs happen in the host cwd, and auxiliary calls are refused. Claude Code and Codex integrate through the tested subagent seam with native OAuth, and the experimental whole-session mode records durable, replayable harness transcripts of external-engine runs. The trade-offs: backend tool rows ship disabled (enabling changes every agent's tool surface; Agent Presets scope it); a whole-session run is one delegation — multi-turn continuation, streaming progress, and live tool echo are not implemented; reasoning and intermediate tool activity stay product-local; the pack's README documents that deleting a route's `models` list serves the full installed catalog, and that a later patch extending the providers dict must restate all routes (patches replace whole configs).
